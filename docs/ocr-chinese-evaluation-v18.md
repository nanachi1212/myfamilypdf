# 中文 OCR 驗證 v18

更新日期：2026-10-08。結論：**維持 Tesseract（`tessdata_fast` 的 `chi_tra`／`chi_sim`），不更換引擎或模型。**

## 方法

用本機 Windows 字型（微軟正黑體、標楷體、新細明體、思源宋體 TC、微軟雅黑）把 6 段繁體與簡體文字各渲染成圖片，共 32 張：乾淨、縮小到 60–70%、加模糊與雜訊。以字元層級比對（忽略空白與標點）計算準確率。`psm 6`，繁體用 `chi_tra`、簡體用 `chi_sim`。

## 結果（平均字元準確率）

| 條件 | Tesseract fast（現行） | Tesseract best | RapidOCR（PaddleOCR 系，Umi-OCR 同類引擎） |
|---|---:|---:|---:|
| 繁體 乾淨 28–30 px | 98.8–100% | 99.4–100% | 79–83% |
| 繁體 縮小 60% | 96.0% | 94.8% | 80.3% |
| 繁體 模糊＋雜訊 | 94.3% | 94.2% | 79.2% |
| 繁體 小字＋雜訊（最差） | 86.8% | 80.4% | 73.4% |
| 簡體 乾淨 | 100% | 100% | 100% |
| 簡體 小字＋雜訊 | 96.3% | 89.2% | 97.6% |
| 全部平均 | **96.6%** | 95.4% | 82.1% |

## 解讀

- PaddleOCR 系預設模型是簡體加英文，繁體字會被辨成相近的簡體或錯字（例如「規定」讀成「视定」）；簡體與 Tesseract 打平。使用者主要是繁體，所以不換。
- `tessdata_best`（約 13 MB 一個語言）整體沒有比 `fast` 好，反而在低解析度更差，不值得增加體積。
- 實際流程是把 PDF 頁面以 300 DPI 渲染後再辨識，比本測試的小圖條件更有利。最差的小字加雜訊情境在真實掃描檔中對應「很糟的影印」，仍有約 87–96%。

## 若之後想再提升

Umi-OCR 的優勢是 PaddleOCR 對簡體與手機翻拍較強；要用於繁體，需換 PaddleOCR 的繁中辨識模型（`chinese_cht`），並新增 Python 推論相依（約 100 MB 以上），不符合「輕量本機」目標。建議先用真實掃描檔確認 Tesseract 不夠用再評估。

測試腳本與圖片未入庫（暫存目錄）；重現方法：以上述字型渲染文字圖片，`tesseract <img> - -l chi_tra --psm 6`。
